シングルサインオン

既存の Microsoft、Google、GitHub のアカウント、または独自の ID プロバイダー（OpenID Connect）でサインインできます。

プロバイダーを設定する

  1. 先に コントロールパネル › 全般 で サイトの URL を設定します。
  2. コントロールパネル › シングルサインオン でプロバイダーを選び、表示された リダイレクト先アドレス をコピーします。
  3. プロバイダーに ThirtyFile を登録し（以下を参照）、そのアドレスを貼り付けます。
  4. 発行された ID とシークレットを ThirtyFile にコピーし、プロバイダーを有効にして保存します。

Microsoft Entra ID

Microsoft Entra 管理センター › アプリの登録 › 新規登録を開きます。「Web」プラットフォームでリダイレクト先を入力し、「証明書とシークレット」でクライアントシークレットを追加します。アプリケーション ID とテナント ID は「概要」にあります。

Google

Google Cloud Console › API とサービス › 認証情報 › 認証情報を作成 › OAuth クライアント ID を開きます。「ウェブ アプリケーション」を選び、「承認済みのリダイレクト URI」にアドレスを追加します。

GitHub

GitHub › Settings › Developer settings › OAuth Apps › New OAuth App を開きます。callback URL にリダイレクト先を入力し、クライアントシークレットを生成します。

OpenID Connect（Keycloak、Authentik、Authelia、Zitadel…）

ID プロバイダーにリダイレクト先を指定した confidential client（Web アプリ）を作り、クライアント ID とシークレットを控えます。ThirtyFile には Issuer URL（Keycloak なら https://auth.example.com/realms/<realm>）と「会社のサインイン」などの サインインボタン名 を入力します。保存すると <issuer>/.well-known/openid-configuration から設定を読みます。issuer は https のアドレスで、設定文書内にも同じ issuer が必要です。

プロバイダーはメールアドレスを含め、確認済みとする必要があります（email のスコープと claim、email_verified）。そうでなければ本人によるリンクのみ可能です。許可ドメイン、ドメイン規則、リンク、自動アカウント作成はほかのプロバイダーと同じです。

サインインできる人

初めてサインインする人への規則は、プロバイダーごとに設定します。

規則動作
リンク済みアカウントのみ本人がアカウントメニューでリンクした人だけ
メールで既存のユーザーと照合メールアドレスが、パスワードも 2 段階認証もないアカウントのユーザー名と一致する人。同じメールのシングルサインオンで作ったアカウントなどが対象です。管理者が作ったものなど、どちらかを持つアカウントは、その認証を迂回させないため照合しません。本人が一度パスワードでサインインして アカウントをリンク します
アカウントを自動作成許可されたメールドメインの人に新しいアカウントを作成

自動作成では、自分たちの人だけが入れるよう、example.com などの 許可するメールドメイン を列挙してください。

ドメインごとの設定

メールドメインの規則で、新規アカウントの権限、スペース容量、グループを変えられます。たとえば partner.example の取引先には小さなスペースを与え、共有を許可しない設定ができます。

新規アカウントに 個人用スペース の マイファイル を作るか、どの保存場所に置くかも決められます。システム設定に従う なら コントロールパネル › 全般 に従います。保存場所のフォルダーが使えなくてもサインインは可能で、復旧するとそこで「マイファイル」を作成します。

自分でアカウントをリンクする

設定した Microsoft、Google、GitHub、OpenID Connect の各アカウントを、アカウントメニュー › サインイン方法 で誰でもリンク、解除できます。リンクするとパスワードなしで入れるため、リンク前に現在のパスワードと、2 段階認証ならコードを求めます。パスワードのないアカウントはサインイン後 10 分以内に行います。メールで照合された場合も含め、リンクごとにアプリ内とメールで通知します。

許可ドメインの一覧がある場合、そのドメインのプロバイダー確認済みメールを持つアカウントのみリンクできます。リンク済みアカウントには確認済みアドレスだけを保存します。

シングルサインオンで作成したアカウントにパスワードはありません。最後のリンクは管理者がパスワードを設定してからでなければ解除できません。管理者が新しいパスワードを設定すると、リンクも解除します。本人がサインインして再びリンクしてください。

ディレクトリでのサインイン：LDAP と Active Directory

ユーザーが Active Directory、OpenLDAP、FreeIPA にいて、OpenID プロバイダーがない場合、ディレクトリのパスワードでサインインでき、アカウントとグループもディレクトリに追従します。コントロールパネル › ディレクトリでのサインイン を開き、ディレクトリの種類を選んで次を入力します。

  • アドレス。ldaps://dc.example.com（最初から暗号化）、または ldap://dc.example.com と StartTLS を使う。StartTLS を使わない場合、接続は暗号化されず、プライベートネットワーク上のディレクトリにのみ許可されます。ディレクトリの証明書が独自の認証局によるものなら、その認証局の証明書（PEM）を貼り付けます。
  • サービスアカウント。ディレクトリを検索できるアカウント。パスワードはサーバーの鍵で暗号化して保存され、画面には送り返されません。探すだけで、ユーザーのパスワードはそのユーザー自身としてサインインして確認します。
  • ユーザー。検索ベース、ユーザーが入力した内容を表す {username} を含むフィルター、そして安定した ID（アカウントのリンクに使うので、ディレクトリ側で名前が変わっても 2 つ目のアカウントはできません）、ユーザー名、名前、メールアドレスの属性。
  • グループ。ユーザー自身の memberOf の値から、またはそのユーザーをメンバーに持つグループの検索（{dn} を含むフィルター。Active Directory では (member:1.2.840.113556.1.4.1941:={dn}) でグループの中のグループもたどれます）で見つけます。サインインに必要なグループを指定でき、ここのどのグループがディレクトリのどのグループに追従するかも選べます。
ディレクトリユーザーのフィルター安定した IDユーザー名グループ
Active Directory(&(objectClass=user)(objectCategory=person)(|(sAMAccountName={username})(userPrincipalName={username})))objectGUIDsAMAccountNamememberOf
OpenLDAP(&(objectClass=inetOrgPerson)(uid={username}))entryUUIDuid(&(objectClass=groupOfNames)(member={dn}))
FreeIPA(&(objectClass=posixAccount)(uid={username}))ipaUniqueIDuidmemberOf

テスト ボタンは、保存する前に入力した内容を試します。接続（証明書の問題は、信頼されていない認証局、名前の不一致、期限切れなどを文章で）、サービスアカウント、そして指定したユーザー名について、見つかったユーザーと各属性の内容、そのグループです。最初にうまくいかなかったところで止まり、ディレクトリ自身の理由を表示します。

サインインするとき

  • ここにアカウントがないユーザー名はディレクトリで検索され、そのユーザーとしてバインドしてパスワードを確認します。パスワードは保存も記録もされません。手動で作成したアカウント（最初の管理者、管理者が作成したアカウント）は自分のパスワードを使い、ディレクトリには送られません。
  • アカウントは初回サインイン時に作成され（オフにすると既存のアカウントだけをリンク）、個人スペースは シングルサインオン と同様で、ディレクトリの安定した ID でリンクされます。
  • 失敗した試行はパスワードと同様に制限されます。また、すべての推測がディレクトリへのバインドになるため、同じ名前は、どのアドレスからでも 15 分以内に 5 回間違えると一時停止され、推測でディレクトリ自身のロックアウトに達しないようにします。ディレクトリに接続できない場合はそのとおり表示され、パスワードの誤りとは数えられず、始まったときと終わったときに 管理者アラート が 1 回ずつ送られます。パスワードをオフにした 人は、ディレクトリのパスワードも使えません。管理者が必須にした場合は、2 段階認証とパスキーも適用されます。SFTP、WebDAV、FTP、S3 は引き続きアプリパスワードとキーを使い、ディレクトリのパスワードは使いません。

誰かが辞めたとき

15 分ごと、および 今すぐ同期 を押したときに、グループがディレクトリに追従し、ディレクトリから消えた、またはそこで無効にされた（Active Directory の無効フラグ付きアカウント、FreeIPA や 389 のロック）ユーザーのアカウントは無効になり、セッションも終了します。アカウントは削除されず、ファイルは残ります。ユーザーが戻るとアカウントは再び有効になりますが、管理者が無効にしたアカウントは無効のままです。検索が誰も見つけられなかった場合は、検索ベースの誤りの可能性が高いため、誰も無効にしません。ディレクトリに追従するグループのメンバーのうち、ディレクトリ経由でサインインする人は、コントロールパネル › グループ で手動では変更できません。

ユーザー名はフィルターに値としてのみ入れられます。*)(uid=* のような名前は誰にも一致しません。1 つの名前に複数のエントリが一致する検索結果は拒否され、リフェラルはたどらず、すべての検索に時間とサイズの上限があります。

パスワードでのサインインをオフにする

シングルサインオンが動くようになったら、ユーザー名とパスワードでのサインインを完全にやめさせ、ID プロバイダーのルール（多要素認証、退職した人への対応）を全員に適用できます。コントロールパネル › シングルサインオン › パスワードでのサインイン で選びます。

選択動作
全員従来どおり。パスワードでもプロバイダーでも可
管理者のみサインインページにユーザー名とパスワードの欄はなく、プロバイダーだけが表示されます。管理者はサイトの /sign-in/administrator でパスワードを使ってサインインします。どのページからもリンクされていないアドレスで、プロバイダーが止まったり設定を誤ったりしたときの入口になります
誰も使わない管理者を含む全員がプロバイダーでサインインし、パスワードを使えるページはありません

保存するには、有効な管理者が少なくとも 1 人、有効なプロバイダーにリンクされている必要があり、保存する本人もその 1 人でなければなりません。誰も使わない では、本人がプロバイダー経由で一度サインインしていることも必要で、誤った設定をその場で見つけられます。該当する管理者は画面に一覧表示されます。パスワードを全員に開放していない間は、そのような最後の管理者を無効化、削除、標準ユーザーへの変更、リンク解除することはできず、最後のプロバイダーをオフにすることもできません。ThirtyFile は理由を示して拒否します。管理者が誰かのパスワードを再設定すると、その人のリンク済みアカウントが削除されます（上記参照）。それでサインインできる人がいなくなる場合も、同様に拒否されます。

変わるもの：パスワードでのサインイン、パスワードで始めたサインインの 2 段階目、メールでのパスワード再設定（リンクは表示されず、送信済みのリンクも使えなくなります）、パスワードの変更。変わらないもの：アプリパスワード、SFTP キー、S3 キー、FTP のデバイスパスワード。これらはサインイン後に自分で作るもので、アカウントが無効化または削除されるまで使えます。すでに開いているセッションもそのままです。パスキーも同じ選択に従います。ThirtyFile はパスキーをパスワードと同じように保管するためで、パスワードを使えない人のパスキーでもサインインできず、画面にも表示されないので、ID プロバイダーのルールがそのまま適用されます。

プロバイダーが動かずに誰もサインインできないときは、サーバーで次のコマンドを実行します。再起動は不要で、すぐに反映されます。
docker exec thirtyfile thirtyfile password-sign-in everyone
ほかの選択肢は administrators と nobody です。パスワードを全員に開放していない間は、ThirtyFile の起動時にもログに警告が出ます。

ゲストがいる Microsoft テナント

テナント ID を指定すると、そのテナントのメンバーをメールで照合します。他組織のゲストもテナント経由で入れますが、メールはその組織が任意のアドレスを指定できます。そのためゲストのメールでは照合や作成を行いません。パスワードでサインインし、自分で Microsoft アカウントをリンクしてください。

ゲストもメールで照合するには、ID トークンにオプションの claim xms_edov を追加します。アプリ登録の トークン構成 › オプションの要求の追加 › ID › xms_edov を使います。Microsoft がゲストのメールドメインをその組織が所有しているかを示し、そのゲストだけを照合します。

シングルサインオンでゲストを作成

プロバイダーの新規アカウントの初期設定でゲストアカウントを作成を選ぶか、メールドメインのルールでゲストアカウントを有効にします。一致するドメインルールがプロバイダーの初期設定より優先されます。通常の個人スペース設定に関係なく、ゲストの「マイファイル」は作成されません。指定したグループのロールと終了日はゲストの制限に適合する必要があります。不適切なグループへの追加は拒否され、作成途中のアカウントは残りません。これらの初期設定は新規アカウントだけに適用され、すでにプロバイダーに連携したアカウントは変換しません。既存アカウントはユーザーページでアクセスを確認してから変換してください。
