Where the files are

On the storage folder and on every Local folder location, each space is an ordinary folder, and its files are ordinary files with their own names. You can open /storage (the storage folder next to compose.yaml) and find everything there:

/storage/company/…              the company space "All files"
/storage/teams/<space name>/…   team spaces
/storage/users/<user name>/…    each user's "My files"

A space gets its folder when it is created, in the folder of the default storage location (or /nas/teams/…, say, when a NAS added as a Local folder location is the default). These are folder spaces: files copied into them by other programs, over SMB or by a scanner, show up in ThirtyFile, and changes made on the web are made in the folder.

  • Names. A folder is named after the space or the user. Characters a file name can't have become _, and names ThirtyFile would hide (desktop.ini, say) get an _ in front. When the folder is already there, because another space has the same name, a folder with that name was made by hand, or a deleted space left it, the new one gets a number: teams/Sales (2).
  • Renaming. Renaming a space doesn't rename its folder, so programs, SMB shares and backups that use the path keep working. Control panel › Spaces shows each space's folder.
  • Deleting. Deleting a space, or a user with their files, removes them from ThirtyFile only: the folder and the files in it stay on the disk, for you to delete or keep. A new space or user with the same name gets a new folder, never the old files. Moving a deleted user's files to another space moves them on the disk.
  • S3, SFTP and FTP keep files in a content store instead: names made of the file's content (ab/cd/…), with the names and folders only in ThirtyFile's database. Renaming a folder there would copy every file in it. Spaces created while one of these is the default location use the content store, and can be moved to another location later.
  • After upgrading from 0.1 or 0.2, the spaces made before keep their files in the content store in /storage until you convert them to plain folders; spaces and users added since get folders right away.

Adding a location

  1. Open Control panel › Storage locations and click Add storage location.
  2. Choose the type and fill in the address and the login details.
  3. Click Test connection. The location can be saved once the test succeeds.
  4. Make it the default if new spaces should use it.

Provider notes

  • AWS S3: leave the endpoint empty.
  • Cloudflare R2: endpoint https://<account ID>.r2.cloudflarestorage.com, region auto.
  • Self-hosted: RustFS works well. Choose "Self-hosted" and tick "Path-style URLs".
Connections without encryption (plain FTP, or S3 over http) are only accepted for addresses inside your own network.

A location for each space

Under Control panel › Spaces, choose a storage location for a space in the content store (on S3, SFTP or FTP, or not converted yet). Files already in the space can be moved to the new location. The space stays in use while they move. A folder space stays in its folder: to put its files elsewhere, move them to another space.

Folder spaces: a folder on the server as a space

Every space on the storage folder or a Local folder location is a folder space (see Where the files are). You can also show an existing folder on the server, such as a NAS share, as a space. Its files stay where they are, as ordinary files, and can also be changed there, for example over SMB or by a scanner.

  1. Mount the folder into the container, for example -v /srv/shared:/mnt/shared.
  2. Under Control panel › Spaces, click New folder space and enter the path inside the container, /mnt/shared.
  3. Add members as for any team space.

ThirtyFile finds changes made in the folder when someone opens it, and checks every folder space every 15 minutes (change this under Control panel › General), or right away with Check for changes. Files and folders moved or renamed in the folder keep their share links and permissions.

On a disk of the server itself, changes show up by themselves about 12 seconds after they are made: ThirtyFile watches the folders for changes. That doesn't work for NFS or SMB mounts (the server isn't told about changes other computers make there), so those rely on the regular check. With very many folders, Linux's limit on watched folders (fs.inotify.max_user_watches, often 8,192 or more) can be reached; the log then says so, and the regular check finds the rest. Raise it on the host with sysctl fs.inotify.max_user_watches=524288. Every folder counts, in all spaces together (every user has a space of their own).

While a large folder space is being checked, Control panel › Spaces shows how far it got, and the log says how long reading the folder and updating the index took when it took more than 10 seconds. As a guide, on an SSD the first check of a folder with 200,000 files takes about half a second to read and 25 seconds to index; checking it again when nothing changed takes a second or two. Network mounts are slower to read, since every file's size and date are asked for over the network: keep the regular check at 15 minutes or more for large NFS or SMB folders.

Everything done on the web changes the folder itself: uploading, creating folders, renaming, moving, copying, editing and deleting. Moving to a space on another disk copies the files, checks them, then removes the originals.

  • Trash. Deleted items go to a hidden .thirtyfile-trash folder inside the space's folder, so they can be restored. Emptying the trash, or deleting an item from it, removes the files.
  • Earlier versions. When a file is saved over on the web, replaced by an upload or restored to an earlier version, the file it was is kept in a hidden .thirtyfile-versions folder inside the space's folder (as a hard link where the disk allows one, else as a copy), which ThirtyFile never shows as files. Changes made directly in the folder, over SMB say, don't keep versions. When a file is deleted for good, its versions go at the next check for changes.
  • Editing at the same time. When a file was changed in the folder while someone edited it on the web, it isn't overwritten: the web version is saved next to it as name (conflict copy).
  • Downloads. A download that is resumed notices a file that was replaced in the meantime and starts over. A file replaced while it is being downloaded can arrive mixed; download it again.
  • Read-only. Tick Read-only when creating the space, or use Make read-only on it later, to allow browsing, downloading and sharing only.
  • File owners. ThirtyFile writes files as the user in THIRTYFILE_RUN_AS (1000:1000 unless set). That user needs permission to write in the folder. When other programs (a Samba share, say) write files as another user, give both the same group and make the folder group-writable, or set THIRTYFILE_RUN_AS to the user those programs use.
  • Deleting a folder space removes it from ThirtyFile only; the folder and its files stay on the server.
  • Temporary files of office programs and systems (~$…, Thumbs.db, .DS_Store) aren't shown. Symbolic links, names that aren't valid text and other disks mounted inside the folder are skipped; Check for changes lists them.
  • A file that is still being copied into the folder appears once it has stopped changing for a few seconds.

Spaces made with 0.1 and 0.2 keep their files in the storage folder under names made of their content (ab/cd/…). To turn them into folder spaces with ordinary folders, like the spaces created since, see Converting spaces to plain folders.

When a location is offline

Browsing, searching and organising folders keep working. Opening, downloading and uploading are paused, and resume by themselves when the location is back. The space is marked as offline in the meantime.
