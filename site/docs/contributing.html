Contributing

How to report a problem, suggest an idea, or change the code of ThirtyFile.

Everyone taking part follows the code of conduct.

Problems and ideas

  • Open an issue and pick the form that fits: Report a problem, Suggest an idea, Report an accessibility barrier, Improve the guides or Improve the code. The form asks for what is needed to help you.
  • Look through the existing issues first. If yours is there, add to it instead of opening a new one.
Security problems are reported privately. Use Report a vulnerability, not an issue, so the problem can be fixed before it is public.

Changing the code

Nothing is pushed to main directly. Every change is a pull request from its own branch.

  1. Start from an issue. For anything larger than a small fix, agree on the idea there first.
  2. Create a branch from main, named after what it does:
    BranchFor
    feat/share-link-editingSomething new
    fix/upload-resumeA repair
    docs/backup-guideThe website and guides
    chore/update-actionsTools, builds and dependencies
  3. Make the change, and run the checks below.
  4. Open a pull request. Give it a title that says what changes in plain words, and one label. Write Closes #123 in the description to close the issue when it is merged.
  5. Wait for the checks. The tests and the image build must pass before it can be merged.
  6. Merge. The pull request becomes one commit on main, and its branch is deleted.

Checks

Run these before opening a pull request. The same checks run on GitHub.

cd server && cargo test && cargo clippy --all-targets
cd ../web && pnpm typecheck && pnpm lint && node scripts/check-i18n.mjs && pnpm test

The end-to-end test signs in, uploads and previews files in a real browser (Playwright), against a server built from the repository:

cd web && pnpm build && (cd ../server && cargo build --release) && pnpm test:e2e
  • Code, comments and guides are written in English.
  • Text in the interface is written in English in the code, with its Traditional Chinese translation in web/src/lib/i18n/zh-TW/.
  • When behaviour changes, update the guide that describes it, in site/docs/.
  • Logic that changes people's files (formulas, saving workbooks, text encodings) gets unit tests in web/tests/unit/.

Every pull request runs the tests and, at the same time, builds the Docker image and starts it, without publishing it. A change that only touches the website or the guides skips both. Merging into main publishes nothing except the website.

Releases

Merged changes collect on main until a maintainer decides to release them. A release is started by hand: on GitHub, open Actions › Release › Run workflow, keep main selected and enter the new version number, such as 1.2.3, or 1.2.3-rc.1 for a pre-release. Or from the command line:

gh workflow run release.yml -f version=1.2.3

The workflow tests what is on main while it builds the image for amd64 and arm64 and starts it. Once both have passed, that same image is tagged 1.2.3, 1.2, 1 (from 1.0.0 on) and latest, without being built again, and then the workflow creates the tag v1.2.3 and the release on GitHub, with notes put together from the merged pull requests since the last release. The server programs for amd64 and arm64 (taken from the image), their checksums and compose.yaml are attached to it. If a test or the image build fails, nothing is tagged or released. The number must be newer than the last release.

A version with a -, such as 1.2.3-rc.1, is a pre-release: its image is only tagged 1.2.3-rc.1, and GitHub marks the release as a pre-release, so nobody gets it without asking for it. When the pre-release is good and nothing has been merged since, release 1.2.3 from the same commit: the workflow tags the pre-release's image instead of building a new one, so people get exactly what was tried (its version label still names the pre-release).

Licence

ThirtyFile is licensed under the Apache License 2.0. What you contribute is licensed under the same terms.

Dependencies must have a permissive licence: the Rust ones are checked against the list in server/deny.toml, which server/about.toml repeats. The image build collects the licence notices of every crate and npm package into THIRD-PARTY-NOTICES, and fails when a crate's licence isn't on that list.
